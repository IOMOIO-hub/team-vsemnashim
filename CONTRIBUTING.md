# Правила работы над {{PROJECT_NAME}}

## Общий порядок

1. Выбираем задачу в backlog и назначаем одного ответственного GitHub-пользователя. Перед началом проверяем зависимости.
2. Создаём ветку от актуального `main`.
3. Вносим одну логически связанную правку; добавляем необходимые проверки и обновляем документы.
4. Открываем PR, связываем его с issue и назначаем review.
5. Отвечаем на замечания, исправляем проблемы и повторно запускаем относящиеся к изменению проверки.
6. После выполнения Definition of Done сливаем PR через GitHub. Напрямую в `main` не пушим.

До согласования архитектуры не добавляем фреймворки, внешние сервисы или зависимости только ради удобства отдельной задачи.

## Ветки

Формат: `<тип>/<номер-issue>-<краткое-описание>`.

- `feat/12-match-job` — новая возможность.
- `fix/18-job-retry` — исправление ошибки.
- `docs/3-match-scenarios` — документация.
- `test/20-report-fixtures` — проверки без изменения поведения продукта.
- `chore/7-ci-checks` — окружение, CI и другие инфраструктурные изменения.

Номер в примере не является созданным issue. В реальной ветке используем номер задачи своего репозитория.

## Коммиты

Формат: `<тип>: <краткое описание на русском>`.

Примеры:

- `docs: описать сценарий создания анализа матча`.
- `feat: сохранять состояние задачи обработки`.
- `fix: учитывать Retry-After при повторе запроса`.

Один коммит — одно связное изменение. Не смешиваем форматирование всего проекта, новые функции и несвязанные исправления. Не используем сообщения `fix`, `update` или `готово` без объяснения сути. Не коммитим секреты, токены и локальные настройки аккаунта.

## Pull request

PR содержит проблему, итоговое поведение, ссылку на issue и выполненные проверки. Для документации указываем, какие сценарии или требования изменены. Невыполненную проверку описываем прямо, с причиной; наличие плана проверки не выдаём за успешный тест.

Сценарии С1–С5 распределяются между участниками. Каждый участник делает свой содержательный PR и/или review чужого PR. Подписи, авторство и вклад не подменяются общим PR, в котором фактически работал только один человек.

Для практики 1 в отдельных PR допустимы сценарий с критериями, уточнение жизненного цикла Job, правила работы или существенное исправление требований. До начала работы нужно договориться о разделах, чтобы не редактировать один текст одновременно без необходимости.

## Кто и как делает review

- Автор запрашивает review у другого участника, знакомого с затронутым сценарием. Конкретный reviewer фиксируется в PR; плейсхолдеры ответственных заменяются до начала работы.
- Reviewer проверяет соответствие задаче, проверяемость критериев, ошибочные случаи, жизненный цикл Job и ограничения источника данных.
- Замечание содержит проблему, её последствие и вопрос или предложение по исправлению. Если замечаний нет, reviewer указывает, какие существенные части он проверил; выдумывать дефекты ради комментария не нужно.
- Автор отвечает на каждое содержательное замечание. Спорное изменение требований обсуждается до слияния и отражается в документации.
- Автор не утверждает собственный PR от имени другого участника. Если команда состоит из одного человека, выполняется собственный checklist; вопрос внешнего review и разрешённого порядка слияния решается по правилам курса и настройкам репозитория.

Пример содержательного вопроса: «Что произойдёт, если источник вернёт 200, но массив координат короче массива времён? Предлагаю явно описать отказ от карты и сохранение остальных разделов отчёта».

## Definition of Done

Задача считается завершённой, когда выполнены все применимые пункты:

- Изменение соответствует issue и его критериям приёмки; границы задачи не расширены без согласования.
- Для поведения приложения проверен успешный путь и относящиеся к изменению ошибки. Проверки отражают требования, а не просто повторяют код.
- Для документации проверены согласованность терминов, ссылок, сценариев и переходов Job. Противоречащие друг другу требования устранены.
- Выполнены доступные проверки проекта и CI, относящиеся к правке. Причины недоступных проверок явно указаны и согласованы с reviewer.
- Внешний API не требуется для каждого теста: основные сценарии воспроизводятся на фиксированных ответах. Реальные запросы обозначаются отдельно и не выдаются за тест полного покрытия источника.
- Нет секретов и неподтверждённых утверждений о данных. Отсутствующие поля и ограничения API обработаны согласно требованиям.
- README и другие затронутые документы обновлены.
- PR прошёл предусмотренное для состава команды review, существенные замечания разрешены.
- PR слит в `main` разрешённым способом, issue закрыт или содержит ссылку на результат.

Для сдачи практики дополнительно заполняем плейсхолдеры, назначаем issues реальным участникам и добавляем настоящие полные ссылки на их PR в заявку. Подготовленные тексты сами по себе не подтверждают эти действия.
